# Architecture: repository map

What every module and file does, for the lead Claude Code session and its subagents (`CLAUDE.md`). Keep it current when a module or file is added, moved or removed.

**Existing:**
- `server/src/index.ts`: Express app with the case, analysis, finding and deposition endpoints from `api/` when Postgres is reachable
- `server/src/worker.ts`: the ingest worker process
- `server/src/api/`: v2 endpoints: cases and witnesses (`cases.ts`: summaries and detail, counted from each case's whole-case analyses); upload a deposition, read its status, retry, set its date (`PATCH`), and move it to another witness or case by re-reading its stored file (`depositions.ts`); whole-case runs (`caseRuns.ts`, one running analysis per workspace); one finding's detail, the person's decision (`PATCH /findings/:id/review`) and `GET /workspace`, each case's latest analysis's findings for the cross-case screens (`findings.ts`); the whole-case report PDF (`report.ts`); finding lanes and labels (`present.ts`, pure)
- `server/src/jobs/`: pg-boss queues; the ingest job handlers; whole-case runs (`caseRun.ts`, `caseRunBatch.ts`); `analysisKeySet` and `paidCallsAllowed` (`paid.ts`) gate paid calls
- `server/src/adjudicate/`: evidence packets from stored lines (`packet.ts`), the strict `Verdict` schema, the Sonnet prompt and client (`model.ts`, `prompt.ts`), `assess()` (Layer 1, Layer 2, checks, score, priority; pure; used by the scoring tests), the pool runner (`pool.ts`) and the request record (`requests.ts`); the whole-case packet contracts follow below. The two-session check (hybrid adjudication, demo replay, direct and cross-witness discovery) was removed on November 6, 2026; its rows stay in the database
- `server/src/adjudicate/stretchPrompt.ts` rendering (whole-stretch reading): render r2 prints every stretch in transcript order (page:line:part). r1, used before November 6, 2026, could print a passage's trailing context before the next exchange. A stretch-v2 run records its render in `config.stretchRender`; a run created before r2 records when its later requests switched (`config.stretchRenderEarlier`). `scripts/replay-case-run.ts` replays either render; `scripts/accuracy-eval.ts` keeps its frozen set's r1.
- `server/src/evidence/`: the Stage 1 evidence foundation (no model calls): references in each transcript's own scheme (`references.ts`), an exchange's stable key, text hash and speaker status (`exchange.ts`, pure, also used by ingestion), and the original-testimony index with retrieval, context, coverage and indexing (`store.ts`). Sessions are `deposition_sessions`; a deposition row is one file, with `session_id` and `session_part`. `server/src/eval/storedExport.ts` reads a stored deposition exported for the real fixtures (`data/eval/evidence-fixtures-v1.json`); `audit.ts` reports attribution causes, parser-revision artifacts and re-reads a stored document in place; `epoch.ts` records the evidence versions a job reads and writes its results through connections that declare them (the guard refuses stale ones, VE002); `correction.ts` is the safe correction built on it (integrity checks, expected-lines gate, fact-unit sync, quarantine in `evidence_quarantine`, plan hash, ledger in `evidence_migrations`, backup, rollback, and the evidence hold that migration 0039's triggers enforce on every derived table; analysis and case-run jobs, ingestion and fact extraction wait or refuse while a document is held). `server/src/adjudicate/packet.ts` shows each exchange only the turns it owns of a shared statement (render `spans-v1`); `server/src/eval/evidenceFixtures.ts` holds the real-data checks. `server/src/ingest/segments.ts` finds speaker changes inside an archive statement, stored in `line_segments`
- `server/src/evidence/eligibility.ts` (pure): classes each answer group as witness testimony, attorney colloquy, objection, exhibit, cover or signature, errata or correction, or unknown, from speakers, position and reporters' wording; retrieval items (`loadItems()` in `server/src/eval/retrievalProbe.ts`) are only witness testimony and unknown (flagged), and `scripts/retrieval-freeze.ts` lists the rest in `excluded-items.json` (errata also in `errata.json`) and reports any labelled side excluded
- `server/src/verify/direct.ts`: pure verification, lanes and deduplication for direct findings
- `server/src/score/evidenceStrength.ts`: the `evidence-strength-v1` checklist for direct findings (pure)
- `server/src/eval/directBenchmark.ts`: scores a direct analysis against synthetic labels by source lines
- `server/src/verify/`: v1's quote matching (`quotes.ts`, moved unchanged), `readAnswer`, shared text helpers, Layer 1 source verification (`source.ts`) and Layer 2 attribution (`attribution.ts`); `safeguards.ts`: deterministic rules (examiner's words, not own knowledge, no recall, the explanation conceding compatibility, an established alternative) that publish a conflict verdict as needs context, never deleting it; applied in `adjudicate/packetAssess.ts` for both contracts (`docs/detection-quality.md`)
- `server/src/score/`: the frozen `RUBRIC_V1`, code's corroboration, context and time checks, `score()` and `prioritize()`
- `server/src/claims/facts/`: Stage 2 fact and event extraction: answer-group units from stored Stage 1 rows with speaker segments as spans (`context.ts`), the model contract and dimension rules (`contracts.ts`), the prompt, batching and estimate (`prompt.ts`), code's source and attribution checks (`verify.ts`, pure), unit coverage, staleness and the Stage 3 read interface `verifiedFacts()` (`store.ts`), `extractFacts()` (`extract.ts`) and `factCoverage()` (`coverage.ts`); the Haiku client is `anthropicFactModel` in `claims/model.ts`. `server/src/eval/factFixtures.ts` runs the hand-authored records of `data/eval/facts-expected-v1.json`
- `server/src/claims/`: statement cards (`cardPrompt.ts`: prompt and page chunking; `cards.ts`: code's checks), the topic map reader (`topicMap.ts`, pure), the Haiku clients (`model.ts`, the only file here that calls the API), shared entity grounding (`verify.ts`, `entities.ts`) and the yes/no answer reader; Stage 2 facts below
- `server/src/retrieve/`: retrieval for whole-case runs (`casePool.ts` and the paths it uses, below); the procedural filter and courtroom word list (`procedural.ts`) and candidate provenance (`provenance.ts`)
- `server/src/eval/`: `synthetic.ts` / `syntheticStore.ts` build the labelled synthetic Webb and Whitfield cases from `data/samples.ts` and `data/whitfield.ts`, used by the whole-case tests; packet and review-set evaluations (`packetBenchmark.ts`, `reviewSet.ts`)
- `server/src/costs/`: model price table (`pricing.ts`), the models v2 calls per stage (`models.ts`), the pure `callCost()`, and `recordCall()` / `jobCost()` over `llm_calls`; `budget.ts` keeps stored budgets and reserves each call's worst-case cost atomically before it is sent
- `server/src/timing.ts`: optional stage timings for benchmarks, written to `BENCHMARK_TIMING_FILE` only when it is set
- `server/src/transcript.ts`: `Q:`/`A:` parser (replaced in v2)
- `server/src/ambiguity.ts`: time-range comparison, reused as-is in v2
- `server/src/data/samples.ts`: Marcus Webb and Elena Ruiz samples, kept as synthetic fixtures
- `tests/`: Vitest tests for the pure functions above
- `scripts/ingest.ts`: ingests one deposition PDF into Postgres from the CLI (development only); `scripts/cases.ts` finds or creates its case and witness by name
- `client/src/`: Veridict, the v2 app. A navy icon rail that opens over the page on hover or keyboard focus, like the Dock (`components/Shell.tsx`, which also opens `components/AddDeposition.tsx` from any page: several files of any supported type in one drop zone, sharing case and witness, or pasted text) leads to Overview, Cases, Depositions, Findings, Analyses and Help; each list has its single screen (`pages/CasePage.tsx`, `DepositionPage.tsx` with the transcript reader and search). Testimony is drawn by `components/Transcript.tsx` as a transcript sheet; `components/FindingParts.tsx` holds the decision buttons, decision dots and the revalidation notice. Whole-case analysis on the case page is `components/CaseRuns.tsx` (the steps, the estimate with its warning and an explicit spending authorization, progress, cancel, resume, the finished state, previous analyses), with each run's coverage and findings on `pages/CaseRunPage.tsx` (`#/case-runs/:id`); its pure rules (lanes mirroring `findingGroup`, coverage wording, budget validation) are `lib/caseRuns.ts`, and case runs have their own budget ceiling, `MAX_CASE_RUN_BUDGET_USD` ($250) in `server/src/api/caseRuns.ts`. Hash routes in `lib/router.ts`; cross-case lists come from `lib/workspace.ts` (`GET /workspace`); `pages/FindingsPage.tsx` lists each case's latest analysis's findings with `lib/findingFilters.ts`; `lib/insights.ts` holds pure derived figures (next step, recent activity, `displayRef`); `lib/review.ts` labels decisions, saved with `PATCH /findings/:id/review`; `lib/labels.ts` holds plain-language wording; `lib/api.ts` the client. Product brief in `PRODUCT.md`.
- `server/src/auth.ts`: public registration with email verification, sign-in, forgot and reset password (scrypt passwords; session and one-time link tokens stored only as hashes), the same-origin check, per-account scoping of every case, deposition, analysis and finding ID, and the gates on uploading (verified email) and paid checks (`users.analysis_access`, granted by `npm run admin`). `server/src/local.ts`: local mode (`LOCAL_MODE=true`): loopback-only listening, paid access for every account, and the loopback-only demo sign-in (`/api/auth/local-demo`, an `@example.test` account only). `server/src/email.ts` sends through Resend (`RESEND_API_KEY`, `EMAIL_FROM`, `APP_URL`), printing to the console in development when unset. The public landing page is `client/src/pages/LandingPage.tsx` with its scroll scenes in `landing.css`; its pictures are real app screenshots in `client/public/landing/`. `server/src/api/remove.ts` deletes depositions and cases with everything that depends on them. `server/src/index.ts` serves the built client from `client/dist` in production; see `docs/deploy.md`, `Dockerfile` and `compose.prod.yml`.
- `server/src/ingest/`: v2 ingestion (`text.ts` reads .txt and pasted text: numbered text keeps its page:line, unnumbered text is stored on page 0 and cited by line, and `verify/direct.ts` holds its findings at needs context): extraction, per-page validation against the `ellison-doj-v1` layout, speakers, exchanges and long-answer parts (pure functions); `rows.ts` maps them to database rows, `store.ts` saves a deposition in one transaction, `uploads.ts` keeps PDFs under `data/uploads/` by SHA-256, and `ingestFile` in `index.ts` runs all three; `ocr.ts` reads scanned files locally with Tesseract into the same page extraction; `pdfText.ts` reads a born-digital PDF with printed line numbers in another layout from its own text; `sessionDate.ts` finds the session date on the cover, offered to the user to confirm (a check needs both dates); `physical.ts` reads a text PDF with no line-number gutter by physical line (layout `pdf-physical-v1`, checked with `hasPhysicalLines`), whose references are labelled as not official and held at needs context
- `server/src/db/`: Drizzle schema (`schema.ts`) and connection (`client.ts`); migrations generated into `drizzle/`
- `docker-compose.yml`, `docker/postgres-init/`: local Postgres, plus a separate `deposition_checker_test` database for the test suite
- `scripts/spike/`: `download.sh` fetches the source PDFs, and `html.ts`, `pdf.ts`, `exchanges.ts` are the independent readers `tests/ingest/real-documents.test.ts` checks ingestion against; production code lives in `server/src/ingest/`
- `docs/agent-log.md`: log of agent sessions

**Planned v2 modules** (folders under `server/src/`, each with one public entry point; see `DESIGN.md`, Modules section): `ingest/`, `claims/`, `retrieve/`, `adjudicate/`, `verify/`, `score/`, `costs/`, `jobs/`, `api/`, `eval/`. Only `claims/` and `adjudicate/` may call a model, and every such call goes through `costs/`.
- Packet adjudication (Milestone 2, evaluation only; never used by normal analyses): the contract in `server/src/adjudicate/packetSchema.ts` (strict per-pair verdicts, three abstentions) and `packetPrompt.ts` (`packet-v1`, the pure formatter); the client `packetModel.ts` (the only file here that calls the API for packets); `packetLoad.ts` resolves frozen retrieval items to stored lines and builds issue and pairwise packets; `server/src/verify/packet.ts` checks a reply per pair: completeness, source (Layer 1 per side, each side's own witness), attribution (Layer 2) and the model's classification, kept separate; `server/src/eval/packetBenchmark.ts` (sample selection, scoring by label, cost) and `mockPacketModel.ts` (label-blind); `scripts/packet-benchmark.ts` runs it. `packet-v2` (Milestone 2.5) sits beside v1 in the same files: eight outcomes (adding compatible, clarification_or_correction, secondhand_or_uncertain) and `detailsCompared` (`packetSchema.ts`), its prompt and formatter with role-tagged lines (`packetPrompt.ts`, `PACKET_PROMPTS` selects a version), and adjacent exchanges loaded by `resolvePassages(..., adjacentOptions)` (`packetLoad.ts`): the logical exchanges just before and after, same deposition, whole, with their own IDs, citable, and recorded by `verify/packet.ts` as `cited: "adjacent"`
- Whole-case runs (`server/src/jobs/caseRun.ts`, table `case_runs`, migration 0036; queue `run-case`; routes in `server/src/api/caseRuns.ts`; CLI `scripts/case-run.ts`): every witness and session of a case. `retrieve/casePool.ts` runs the offline multi-path retrieval (full text, LSA, question, anchors, `F_factual`, MiniLM when its files are present), `buildPool`, `triage` and `groupPool` with their defaults on stored evidence; packets past 8 pairs or about 9,000 input tokens are split deterministically (`retrieve/packetSplit.ts`); a live run then waits in `awaiting_confirmation` with its cost estimate until confirmed with a budget; every pool pair becomes a candidate in the set `case-run-<id>` (`selected`, `uncovered` or `deferred`, each with its reason; `excluded` when its stored lines can't be rebuilt). The packets go into the Milestone 3 ledger with screening off (baseline order, every packet prioritized), its entries carrying candidate, exchange, deposition and session IDs and the run's source hash. Each packet is claimed from the ledger, sent in the run's contract (`packet-c3`, the Focused Analysis default since November 6: packet-v1's packets, rules and verdict fields with a compact reply, the model screening every pair and writing a full verdict only for pairs it does not dismiss; `adjudicate/compactPrompt.ts`, `compactSchema.ts`, and `compactRead.ts`, which turns a reply into packet-v1 verdicts, a dismissal into a stored `false_positive` verdict that never becomes a finding, and rejects a dismissal whose quotes aren't in its exchanges; `packet-v1` for earlier runs and rollback) (budget reservation, `adjudication_requests`, `recordCall` with raw output stored on the entry before parsing), verified by `verify/packet.ts` and scored by `adjudicate/packetAssess.ts` (pure: a verified packet pair to findings fields, with `score()` and `prioritize()`); at most `MAX_RECOVERY_ROUNDS` (two) recovery requests per claim, then the entry is `incomplete` with its unanswered pairs listed. A resumed run parses a stored reply instead of paying again, and never writes a second verdict for a candidate. Live runs found mid-adjudication after a crash become `interrupted`; a request left `sent` is closed as uncertain (counted in full) and its packet is never retried unless a resume asks for `retryUncertain`; mock runs use the label-blind mock and are never billed. The API contract for the frontend is `docs/case-run-api.md`. Packets run in parallel (`concurrency` lanes per run, each claiming from the ledger with skip-locked claims) under `jobs/limiter.ts`, one `ProviderLimiter` per worker process: a global in-flight limit shared fairly between runs (a freed slot goes to the run holding fewest), the provider's RPM/ITPM/OTPM as continuous token buckets (input charged from an estimate and corrected to uncached input plus cache writes; output admitted against each request's max_tokens worst case and refunded down to the actual output when the reply arrives, in full after a 4xx, never after an uncertain failure, so requests in flight can't together pass the output limit), and a shared pause after a 429 or 529 (retry-after, else the RFC 3339 reset headers). **The limits are per worker process**: two worker processes each use the whole configured limits, so with several workers divide the `PROVIDER_*` values between them (or coordinate them in Postgres first). A lane whose reservation fails while the run's other requests hold reservations waits for one to settle; `blocked_budget` only when nothing is held. Every lane finishes before the run stops, is interrupted or rethrows. The worker reads `CASE_RUN_PACKETS_PER_CASE`, `CASE_RUN_PACKETS_GLOBAL`, `CASE_RUN_MAX_CASES` and `PROVIDER_*` (`caseRunSettings`), and on shutdown drains (stops claiming) for 60 s before aborting what is in flight. A spend-cap 429 (`enforced_spend_limit_reached`) fails the run at once and is never retried. A packet's verdicts and findings are written in one transaction with batched statements (candidates locked in id order); `verdicts_candidate_idx` (migration 0037, not unique: a candidate may hold several verdicts across replays and analyses) keeps the per-packet verdict checks off a full scan. **Economy execution** (`case_runs.execution = 'batch'`, migration 0038) sends the same packets through the Message Batches API: `jobs/caseRunBatch.ts` runs the run as short ticks (reconcile a batch left `submitting` by a crash from the provider's list, poll, import ended batches' results by `custom_id` exactly once, advance each ledger entry, submit new batches with every request's worst case reserved at batch prices), and the case-run job queues the next tick (`CASE_RUN_BATCH_POLL_SECONDS`) while batches are open; the worker re-queues ticking runs on start. Batches are `case_run_batches` rows; their requests are `adjudication_requests` rows (`case_run_batch_id`, unique `custom_id`, `screening_entry_id`, `round`, `retry_of`). Both modes share `entryContext`, `nextStep` and `applyReply` in `caseRun.ts`, and the request body `packetRequestParams` in `adjudicate/packetModel.ts`; `adjudicate/packetBatch.ts` is the only file that calls the Batches API for packets, and `eval/mockPacketBatch.ts` is a fake provider (out-of-order and duplicate results, errors, expiry, cancellation, lost submissions) for tests and test-model runs. **Whole-stretch reading** (experimental, off unless `ALLOW_STRETCH_V2=true`; `docs/whole-stretch-v2.md`): a run created with contract `stretch-v2` (its `promptVersion`) builds stretch requests instead of issue packets (`retrieve/stretchSet.ts`, a `PacketSet` over the triage-kept pairs), so the ledger, Fast, Economy, recovery, accounting and coverage are unchanged; `adjudicate/stretchPrompt.ts` holds the pilot's prompt and schema and renders production passages; `adjudicate/stretch.ts` verifies every finding with `verify/packet.ts` and derives one status per pair; flagged pairs are persisted and scored as packet-v1 findings, and pairs read with no finding get a verdict and no finding (never "compatible"). A run may be limited to selected depositions (`config.scope.depositionIds`, `buildCasePool` `depositionIds`; the case page's guided analysis in `client/src/components/CaseRuns.tsx` starts both kinds). Retrieval runs in near-n^1.5 time: the sparse, anchor and dense paths keep their top k with bounded heaps and score each dense pair once in tiles, `F_factual` scores only partners an inverted index can reach, and the residual-star hub comes from a heap (all exact: identical pools, triage and packets). Two further exact options, `pathA: "memory"` (`retrieve/fullTextMemory.ts`: Postgres parses, the ranking reproduces `ts_rank_cd` for Path A's OR queries in memory; `tests/db/fullTextMemory.test.ts` checks it against Postgres) and `denseThreads` (`retrieve/denseParallel.ts`, worker threads), are read by case runs from `RETRIEVAL_PATH_A` and `RETRIEVAL_DENSE_THREADS`. Each packet's output cap is one value (`packetMaxTokens`): sent as max_tokens, reserved, admitted by the limiter and stored; `PACKET_OUTPUT_TOKENS_PER_PAIR` may only lower it, and a recovery request uses the default. `buildCasePool` takes an optional `selection` (`perSession`/`perWitness` quotas with a `minShare` relevance floor, `perPath`; `retrieve/frozen.ts` `buildPool`), off by default, measured by `scripts/retrieval-variants.ts`. **Exact-request reuse** (migration 0041): `adjudicate/requestReuse.ts` (pure) fingerprints the provider-visible request (`packetRequestParams` plus the adjudicator's model and effort) and keys the evidence it was built from (depositions, witnesses, parser versions, evidence epochs, line ids); `jobs/requestReuse.ts` finds a `completed` source request of a live run of the same case with both keys and records a `reused` request (no call, no reservation, cost 0, a database check) whose source text goes through `applyReply` again. Both modes call it where they would send (`adjudicateEntry`, `caseRunBatch.ts` `advance`); the worker turns it on (`REQUEST_REUSE`, on unless `off`); the report counts `requests.reused` and `cost.reuse.avoidedUsdEstimate`
- Evidence screening (Milestone 3, experimental; never used by normal analyses, never calls a model): `server/src/screen/contract.ts` (`screen-contract-v1`: one result per packet, prioritized, deferred or consolidated, priority as an ordering key only, adjudication state kept apart; `accountFor()` checks every pool pair ends in one packet or `uncovered`), `strategies.ts` (pure: baseline, fused, minilm, deterministic, coverage, optional consolidate), `ledger.ts` (tables `screening_runs` and `screening_entries`: record a run, claim work, adjudicate once, retry, release after a crash, extend the budget, find stale evidence; never deletes); `server/src/eval/screeningBenchmark.ts` and `scripts/screening-benchmark.ts` measure it offline. See `docs/milestone-3-screening.md`
